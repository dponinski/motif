A new design tool built for design systems first

## Getting started

Needs Node 20 or newer.

```bash
npm install
cp .env.local.example .env.local   # then fill in what you need; nothing in it is required to look around
npm run dev                        # http://localhost:3000
```

| Command | What it does |
| --- | --- |
| `npm test` | The unit tests. Those that need a PostgreSQL database run when `TEST_DATABASE_URL` is set, and are skipped without it. |
| `npm run typecheck` | TypeScript, without building. |
| `npm run lint` | ESLint (Next 16 no longer has `next lint`). |
| `npm run build` | The production build. |

The same typecheck, lint and tests run on every pull request (`.github/workflows/ci.yml`).

### Browser suites

`e2e/` holds the end-to-end suites: each drives the real editor in a browser (Playwright) against fake GitHub, CDN, mail and sign-in servers, so nothing outside the machine is touched. They are the coverage for the UI.

```bash
npm run e2e:setup    # once: the packages the fake CDN serves (e2e/cdn)
npx playwright install chromium   # once: the browser
npm run e2e          # every suite that needs no database (starts the app itself)
npm run e2e:db       # accounts, sync and teams: needs PostgreSQL
node e2e/run.js edit tokens   # named suites
```

- `npm run e2e` starts `next dev` on port 3000 (or `next start` with `E2E_PROD=1` after `npm run build`; `E2E_REUSE=1` uses a server that is already running). The suites that start a server of their own use port 3100.
- The database suites make a database for the run. They connect as an administrator to create it (`E2E_DB_ADMIN_URL`, default `postgresql://postgres@127.0.0.1:5433`) and the app connects as the role that owns it (`E2E_DB_APP_URL`, default `postgresql://motif:motifpw@127.0.0.1:5433`, so that role has to exist).
- Screenshots the suites take go to `e2e/out/` (not kept in git). Shared pieces (the fake servers, seeding a project) are in `e2e/support/`.
- CI runs both groups on every pull request, against a production build.

## What Motif is

A design system builder. It works on the React components and design tokens of a GitHub repository: it reads them, shows them running, lets a designer change them visually and assign tokens to them, documents them, and sends every change back as a pull request. The code in the repository is the source of truth; Motif keeps nothing that the repository doesn't have except documentation and unsent edits. It is not a prototyping tool: there are no shapes, frames or free-form layouts, only the components and tokens of the repository.

## Projects

Each design system is a **project**: one GitHub repository, with its tokens, documentation, imported components and unsent edits. The dashboard lists them. **New project** (or **Connect a repository** on an empty dashboard) takes `owner/name` or a GitHub URL and an access token. Public repositories can be read without one; private ones, and opening pull requests, need a fine-grained token limited to the repository with Contents and Pull requests read and write. The repository is checked before the project is made, so a typo or a missing token shows in the dialog. A token already entered for another project can be reused.

Projects are kept in this browser (local storage), token included, and are saved a moment after the last change (and when the page is left). Renaming or deleting a project only affects this browser: the repository is not touched, and edits waiting to be sent as a pull request are kept. A new project starts with no tokens and no components: scan the repository (see below) and sync its tokens. A project's tokens are saved (in the browser and on the server) as typed tokens (a **Color**, **Number** or **String**, with its unit and where it belongs) and **compositions** (a text style, a shadow) rather than as one list per kind; a project saved by an earlier version is read in that shape automatically, and a page left open from before is told to reload instead of saving the old shape back.

Versions of Motif that were built around design files (`.motif.json` files saved to a branch, with their own sync) are gone, and so are the files, connections and token sets they left in the browser: they are cleared the first time the dashboard opens. Documentation now lives in the project in this browser, not in the repository.

## Signing in with GitHub

Instead of creating and pasting an access token for every repository, a person can **sign in with GitHub**. It uses a **GitHub App** that you create once for your Motif deployment; the app is then installed on the accounts and repositories that should be usable, and each person signs in to approve it.

- **What it gives**: **New project** lists the repositories the app is installed on, to pick from (no `owner/name` to type, nothing to paste), and a project made that way stores no token at all. Scanning, reading a private repository and opening pull requests use the signed-in person's access through the app, and the pull request is opened as them. The app can only reach a repository where it is installed and the person has access. A token typed in for a project is still used for that project, and a public repository can still be added by name with no sign-in. Nothing changes where the server isn't set up for it: the button doesn't appear.
- **Where the tokens are**: the browser is sent to GitHub to approve, GitHub sends it back with a code, and the server exchanges the code for tokens (the exchange needs the app's client secret, which never reaches the browser). The tokens are kept in a cookie the page's scripts can't read (`httpOnly`, `SameSite=Lax`, only sent to `/api/github`, `Secure` on https). The page asks the server for the access token (it lasts 8 hours) and keeps it in memory only; nothing is saved in local storage. The refresh token never leaves the cookie, and renewing needs the client secret too, so it is of no use on its own.
- **Renewing**: a token about to stop working is renewed by the server before it is handed out. If GitHub still refuses a token (revoked, or ended early), the page asks for a new one and repeats the request once, and requests refused together share one renewal. GitHub gives each refresh token one use, so the server also lets two requests that carry the same one (two tabs) share the result for a minute instead of racing. When the refresh token is refused or has run out (after about six months) the person is told the sign-in has ended and signs in again. If GitHub can't be reached the sign-in is kept.
- **Signing out** clears the cookie and revokes the access token at GitHub.
- **A cancelled or refused sign-in** comes back to the page it started from with a message. A sign-in that wasn't started in this browser (the state doesn't match) is not finished. The page to come back to can only be a path on this site.

**Setting it up**

1. Create the app: GitHub, *Settings*, *Developer settings*, *GitHub Apps*, *New GitHub App* (for an organization, under the organization's settings instead). Give it a name and a homepage URL.
2. **Callback URL**: `https://your-domain/api/github/callback`. It must match exactly where the site is served. An app can have several callback URLs (add `http://localhost:3000/api/github/callback` to try it locally, and each deployment you want to sign in from; a preview deployment on another address can't sign in unless its callback is listed).
3. **Expire user authorization tokens**: leave it on (the default). **Request user authorization (OAuth) during installation** can stay off. **Webhook**: untick *Active*; Motif doesn't use one.
4. **Permissions**, under *Repository permissions*: **Contents: Read and write**, **Pull requests: Read and write**. *Metadata: Read-only* is added for you. Nothing else is needed.
5. **Where can this app be installed**: *Only on this account* for your own repositories, *Any account* for others'.
6. Create the app, then **generate a client secret** and note the **Client ID** and the app's **URL name** (the last part of `github.com/apps/<name>`).
7. **Install the app**: *Install App* in the app's settings, on the account or organization that owns the design system repositories, for all or selected repositories.
8. Set these on the server (Hostinger: the Node.js app's environment variables) and redeploy:

| Variable | What |
| --- | --- |
| `GITHUB_APP_CLIENT_ID` | the app's Client ID |
| `GITHUB_APP_CLIENT_SECRET` | the client secret, kept on the server only |
| `GITHUB_APP_SLUG` | the app's URL name, for the link to install it on more repositories |
| `APP_URL` | where the site is served, `https://your-domain`, when it sits behind a proxy that doesn't pass its address on (it has to match the callback URL) |

The server keeps what it needs to share a renewal in memory, so it expects to run as one process. A static export (the desktop build) has no server, so there is no sign-in there and access tokens are used.

## Accounts

Without a database, Motif has no accounts: it is a single-user tool, as before, and everything is kept in the browser. With `DATABASE_URL` set, people can sign in to Motif itself (not just to GitHub for repositories) and the assistant is only for people who have. It needs a PostgreSQL database (the tables are made on first use); Supabase is what it is set up for, see below. Who may sign in is a list you control; there is no sign-up.

| Variable | |
| --- | --- |
| `DATABASE_URL` | `postgresql://user:password@host:5432/database`. Turns accounts on. With Supabase: **Connect → Session pooler** and your database password (see below). |
| `DATABASE_CA` | Optional: the CA certificate (PEM; write its line breaks as `\n`) to check the database server against. Without it the connection is encrypted but the server isn't verified. |
| `ALLOWED_EMAILS` | Who may sign in: addresses and `@domain` entries separated by commas or spaces (`ada@example.com, @acme.io`). **Empty means nobody**: the sign-in dialog says so. A person is matched on an address their provider has *verified*, so the same person signing in with email, Google, Apple and GitHub is one account. The list is checked again on every request, so removing someone ends their sessions. |
| `APP_URL` | Where the site is served (`https://motif.example.com`). Needed behind a proxy and for the callback addresses below. |
| `SMTP_URL`, `MAIL_FROM` | Turns on **email links**: `smtps://user:pass@smtp.example.com:465`. A link works once, for 15 minutes, opens a page that asks for a press (so mail scanners can't use it up), and is only sent to addresses on the list, with the same answer shown for any address. |
| `GOOGLE_CLIENT_ID`, `GOOGLE_CLIENT_SECRET` | Turns on **Google**. In the Google Cloud console create an OAuth client of type *Web application* with the redirect URI `APP_URL/api/auth/google/callback`. |
| `APPLE_CLIENT_ID`, `APPLE_TEAM_ID`, `APPLE_KEY_ID`, `APPLE_PRIVATE_KEY` | Turns on **Apple** (needs a paid Apple Developer membership and an https site). Create a Services ID (that is the client id) with the return URL `APP_URL/api/auth/apple/callback`, and a *Sign in with Apple* key (the `.p8` file is the private key; write its line breaks as `\n` if it goes in one line). People who hide their email from the app can't be matched to the list; they are told to share it. |
| GitHub | Uses the GitHub App of "Signing in with GitHub". Give the app the account permission **Email addresses: Read-only**; without it nobody can sign in that way, as there is no verified address to go by. |
| `CHAT_PER_HOUR` | How many assistant messages one person may send an hour (default 60, `0` for no limit). |
| `AI_PUBLIC` | Without a database the assistant is open in development and **closed in production** (it spends your Anthropic key); `AI_PUBLIC=true` opens it to anyone who reaches the site. |

How it is kept safe: a session is a random value in an `HttpOnly` cookie of which only a hash is stored; it lasts 30 days from the last visit; sign-in and the assistant refuse requests that don't come from the app itself; links, sign-in attempts and chat messages are rate limited per address and per place; Google and Apple sign-ins use a state, a nonce and (Google) PKCE and check the ID token against the provider's keys; errors are never put in the page beyond a short reason.

### Using Supabase as the database

Create the project, then in **Connect** copy the **Session pooler** connection string (`postgresql://postgres.<ref>:<password>@aws-0-<region>.pooler.supabase.com:5432/postgres`) into `DATABASE_URL`. Use the pooler, not the "Direct connection": direct connections are IPv6-only unless you add Supabase's IPv4 add-on, and most hosts (Hostinger included) are IPv4. The transaction pooler (port 6543) works too.

- **The tables are made by the app** the first time it connects (and kept up to date when a new version needs more), so there is nothing to run by hand. They live in the `public` schema with **row level security on and no policies, and no rights for the `anon` and `authenticated` roles**: Supabase's public API (the one the publishable key opens) can't read or write any of them. Only the server, through `DATABASE_URL`, can. Don't add policies or grants to them: the sessions, sign-in links and saved projects are in there.
- Motif talks to the database only from the server, with `pg` and `DATABASE_URL`. It doesn't use Supabase's client libraries or its API keys, so it needs no `NEXT_PUBLIC_SUPABASE_*` settings.
- Keep the database password out of git: it goes in the host's environment variables (or `.env.local`), never in `NEXT_PUBLIC_` ones.

### Projects saved to your account

Signed in, a person's projects are saved to their account and kept the same on every device they use. The browser still works on its own copy, so Motif works offline and edits are never held up by the network; changes are sent a moment after they are made, and other devices are checked every 45 seconds and whenever the window is focused.

- **What is saved**: the project's name, its repository (owner, name, default branch), its tokens, the link to the repository's tokens, and its documentation. **Not** saved: access tokens (they stay in the browser they were typed into, and anything that looks like one is refused by the server), the repository scan and the component library (read again from the repository), and unsent edits to components. On another device a project has no token of its own: sign in with GitHub, or type one.
- **First sign-in**: the projects already in the browser are saved to the account, and the account's projects are brought in. Up to 100 projects per account.
- **Two devices**: each project is compared in five parts (name, repository, token link, tokens, documentation) against what both sides had when they last agreed. A part changed on only one side is taken from that side, so docs edited on one device and tokens on another are combined. Only the *same* part changed differently on both asks a person, once, which version to keep. Nothing is sent for that project until they answer. A project deleted on one device is deleted on the others (unless it was changed here, which asks), and the server keeps a note of the deletion for 90 days.
- **Tokens and pages are merged item by item.** Each color, spacing step, radius, shadow, typography style and set in the tokens, and each documentation page, is an item. Motif keeps a hash of each from the last time the two sides agreed (not the content), so when two people (or devices) changed the same part, an item changed by only one of them is taken from that one (added, edited or deleted), and only an item changed differently by both is asked about, by name (“both changed the token “primary””); everything else from both people is kept whichever answer is chosen. An item edited by one and deleted by the other is asked about too. The name, repository and token link are still decided as a whole, and so are tokens and pages for a project whose agreement predates this (until its next sync). What one browser has staged among its unsent changes (`staged` in the token link) isn't synced, so it never causes a question.
- **Signing out** takes the account's projects off that browser (after sending anything not yet sent), so the next person to use it doesn't see them; a project that couldn't be sent stays for its owner. A different person signing in on the same browser never receives another account's projects.
- Projects are stored as JSON in the `projects` table (a team's in `team_projects`), one row per project with a version number that rises with each change; a device that was behind is refused instead of overwriting.

### Teams

A team shares design systems between people. Make one from the dashboard (**New team**, for people on the server's list); its design systems are a section of the dashboard of everyone in it.

- **Two roles.** Owners invite and remove people, rename the team, change roles, delete the team (once it has no design systems), and delete a design system for everyone; members edit the shared design systems and can leave. A team always has an owner. Up to 10 teams per owner, 50 people and 100 design systems per team.
- **Inviting.** An owner enters an email address in the team's dialog. The address is mailed a link (with `SMTP_URL` set; without it the dialog shows the link to pass on) that works for 14 days, and an invitation also waits on the dashboard of whoever signs in with that address (**Join**). It is taken up by the address that was invited, never by whoever has the link. Re-inviting replaces the earlier link; owners can cancel.
- **Guests.** An invitation lets the address sign in even when it isn't in `ALLOWED_EMAILS`: such a person is a *guest*, who gets their teams' design systems and nothing the server pays for (the assistant is refused and not shown, and they can't start teams). Access is checked on every request, so taking someone out of their last team ends it at once (people on the list are unaffected).
- **Sharing a design system.** **New project** and a project's menu (**Move to …**) put a design system in a team; owners can move one back to their own. Members' changes go to the same stored design system with the same version check as for two devices, so nobody overwrites anybody: a part changed by two people at once is narrowed to the items they both changed (see below) and only those are asked about. Each card shows who changed it last. Teammates see changes when they next look (focus, or within about 45 seconds); there is no live presence.
- **Leaving or being removed.** The team's design systems leave that browser, unless the person has changes of their own in one, which are then kept as their own project. A member can't delete a team's design system (the server refuses too); an owner's delete is for the whole team.
- **GitHub stays personal.** Every GitHub request is made from the browser with that person's own GitHub sign-in or token, and a token is never part of what is shared. A teammate with no access to the repository is told to ask an owner. Each person who presses Sync opens their own branch and pull request.

Preview deployments get their own address, so Google, Apple and GitHub sign-in work there only if that address's callback URLs are registered with the provider. Email links work anywhere.

Tests that use a database run when `TEST_DATABASE_URL` points at an empty one (`TEST_DATABASE_URL=postgresql://user:pw@127.0.0.1:5432/motif_test npm test`) and are skipped without it.

## Going live

Everything here is tested against stand-ins (a fake GitHub, a fake OpenID provider, a mail sink), which can only be as right as what they were written from. Before relying on a deployment, check it against the real ones. Two commands do most of that; the rest is one real sign-in each.

**`npm run doctor`** reads the environment the server runs with (the shell's, and `.env.local`) and asks each part whether it is accepted, without changing anything:

```bash
npm run doctor
npm run doctor -- --send-to you@example.com    # also sends a real sign-in link and a real invitation
```

- **Database**: connects, shows the version, says whether the tables are there and at which step (the app brings them up to date when it starts), and whether the server's certificate is being checked.
- **Who may sign in**: that `ALLOWED_EMAILS` isn't empty (empty means nobody) and holds addresses or `@domains`.
- **APP_URL**: that it is the address the site is served at, and the exact callback addresses to register with each provider.
- **Email** (sign-in links and team invitations use the same server): logs in to `SMTP_URL`, checks the sender, and with `--send-to` sends the two real messages so you can see them arrive (and whether they land in spam). Without `SMTP_URL`, invitations show their link to pass on instead.
- **Google**: that Google describes itself and publishes keys, and, by offering the token endpoint your client id and secret with a code that can't be right, whether Google knows the pair (it answers *invalid grant* if it does and *invalid client* if not).
- **Apple**: that the private key reads and signs the client secret, that the site serves Apple's domain file (below), and, in the same way, whether Apple accepts the Services ID, team and key together.
- **GitHub App**: whether GitHub knows the client id and secret, that the app named by `GITHUB_APP_SLUG` exists, and that it has the permissions Motif needs.

It exits with an error if something is wrong, so it can run after a deploy. What it can't know is whether a **redirect address** is registered with the provider: only the first real sign-in shows that, and the doctor prints the address to register.

**The things that catch people out**

- **Google**: on the OAuth consent screen, an app left in *Testing* only lets the test users you list sign in, and ends their access after 7 days. Set it to *In production*; Motif asks for nothing but `openid email profile`, which needs no review. The redirect URI is `APP_URL/api/auth/google/callback`.
- **Apple**: needs a paid developer account and an https domain of your own (not `localhost`). On the Services ID, register the domain and the return URL `APP_URL/api/auth/apple/callback`, and Apple gives a file to download that proves the domain is yours: put it at `public/.well-known/apple-developer-domain-association.txt` in this repository and deploy, before pressing Verify. The key must be one made for *Sign in with Apple*; its `.p8` text is `APPLE_PRIVATE_KEY`. People who hide their email come back as a `@privaterelay.appleid.com` address, which no list can name, so they are told to use another way to sign in.
- **Mail**: send from an address on a domain you control and set up for it (SPF and DKIM are in your mail provider's settings; without them links go to spam). `smtps://` is port 465, `smtp://` is 587 and starts TLS by itself. A password with symbols is percent-encoded in the URL.
- **GitHub App**: the callback URL must be listed on the app (`APP_URL/api/github/callback`); the account permission **Email addresses: Read-only** is what lets people sign in to Motif with GitHub, and **Contents** and **Pull requests** (read and write) are what Sync needs. Install the app on the repositories that should be usable.

**`npm run live:github`** runs Motif's own GitHub client against a real repository instead of the stand-in: it reads the repository, makes a branch of its own (`motif-live-check/…`), commits several files in one commit, checks that a write over a file that has moved on is refused as stale, opens a pull request, reads and edits it, and then closes the pull request and deletes the branch. Nothing is written to the default branch.

```bash
LIVE_GITHUB_REPO=owner/name LIVE_GITHUB_TOKEN=github_pat_... npm run live:github
LIVE_GITHUB_PR=0 ...    # leaves out the pull request, which is what starts a CI run on the repository
```

Use a fine-grained token for that repository with *Contents* and *Pull requests* read and write, preferably a throwaway repository. The commits say `[skip ci]`.

The last check is done by hand, once per way of signing in, in a private window: sign in, sign out, sign in again (it should be the same account), and for email links open the same link twice (the second time it says the link has expired or was already used). For teams: invite a second address, open the invitation in another browser, and sign in with that address.

## Starting from an empty repository

A project doesn't need a repository that already has components or tokens. Connect any repository, empty or not, and Motif **pulls it by itself** when the project is first opened: the scan, the components found in it (they appear in the Components panel), and its tokens, which come into a Motif set named for the repository (the set every project starts with, when it is still empty) and are linked to it, so a token made here is usable at once and goes out with the other changes. A repository with no tokens (and no Tailwind v3) is linked to the whole project, to be sent with the first push as design tokens files (a Tailwind v3 repository with no tokens keeps the stylesheet sync, with the project's first set). A project opened before this existed is linked the first time it is opened. A repository with no components lands on the **build screen**: where to start, with nothing created for you.

- **No commits yet.** A brand-new repository with no commits has nothing to branch from, so no pull request can be opened against it. The build screen (and the Source control panel) then offers **Create README.md on `main`**: one explicit step that makes the first commit straight to the default branch, a README and nothing else. It is the only change Motif ever makes directly to a branch; everything after goes through a branch and a pull request. It needs sign-in with GitHub, or an access token, that can write to the repository.
- **Tokens, from scratch.** On the Tokens screen, add colors, spacing, radii and shadows as you would anywhere. **Push** (in Source control) puts every set in your pull request as [design tokens files](src/lib/dtcg/README.md) (sent with **Push**, like everything else): `src/tokens/tokens.json` (and a file per extra theme, and `tokens.config.json`), the stylesheet they come to (`src/styles/tokens.css`: with Tailwind v4, the variables in `@theme`; otherwise `:root { --color-primary: #3366ff; }`, with a selector per extra theme), a `style-dictionary.config.mjs` and a `tokens:build` script that build the same stylesheet in the repository (`npm run tokens:build`, Node 22+; a `package.json` is made when there is none), and the stylesheet imported after Tailwind's when it is there. It needs no framework: import the stylesheet wherever your application loads its styles. The preview applies your tokens as you edit them.
- **Add a framework.** **Add a framework** (the build screen) adds a framework to the repository like a dependency, in your pull request. **Tailwind CSS v4** is the first: it adds `tailwindcss` to `package.json` (a new one if there is none; an existing one is edited by text, so nothing else in it changes), a stylesheet `src/styles/tailwind.css` with `@import "tailwindcss"` (and an import of the tokens file, when Motif made one), and, when the tokens are design tokens files, says Tailwind in their config and writes the stylesheet again with the variables in `@theme` (a stylesheet of CSS variables Motif made is rewritten the same way). It refuses when the repository already has Tailwind v3 or v4. Motif edits styles with Tailwind's classes as soon as it is added (the preview starts Tailwind), and the repository has it once the pull request is merged. Adding it twice is refused (it says it is already in your pull request). What it does not do: set up the bundler of your application. It says so in the pull request, which lists what is left to do.

### Building a component from nothing

**New component** (the build screen, or the **+** in the Components panel) makes a component to build on the canvas. Give it a name (`Button`, `PricingCard`) and Motif makes, as changes you can see and undo, and not yet in the repository:

- `src/components/Name.tsx` (in the folder where the repository's components already are), a function component that starts as a single element;
- `src/components/Name.css`, the stylesheet next to it, with the rule of its root class (`.name { padding: 16px; }`). In a repository that uses **Tailwind v4** there is no stylesheet: the component is made of utility classes, like the repository's others;
- a line exporting it from the repository's entry file (`src/index.ts`, made if there is none), so it is part of what the design system exports;
- a `package.json` that lists React, if the repository's doesn't (made if there is none): components are only read from a repository that depends on React, so without it a merged component wouldn't be found again.

It opens in Design, running, and is marked **new** in the list. Everything in the inspector works on it, with the styles written **into the stylesheet**: each element gets a class of its own the first time it is styled (named for the component and the tag, `button__h2`), and the rule for that class gets the declaration. Controls are the same as for classes (layout, spacing, size, type, fill and border), a token picker offers the repository's CSS variables by name (`var(--space-2)` for a token called `space-2`), and a value written out where a token could be is marked, with the token it matches one press away. **States** (hover, focus, active, disabled, dark) write the rule for the state (`.button:hover`, `.dark .button`); the breakpoints write `@media (min-width: …)` rules, narrower first. What Motif can't place (an element whose `className` is computed, a state it can't write in CSS) is refused with the reason. A rule that other elements share changes for all of them, and the inspector says so.

The stylesheet edits show in the preview as you make them. Changes to several files (a new component and its stylesheet, an element and the rule that styles it) are one step to undo. Sending them is **Sync** (see below): new files show as all additions. A component made here stays in the list, marked new, while its pull request is open; once the pull request is merged it is read from the repository like any other component.

Not here yet: variants for components styled with a stylesheet (their props can be edited), CSS Modules and other frameworks, and teams.

## Documentation

The Docs view in the editor builds design system documentation from the project. Every token category has a page from the start (swatches, type, spacing, radius and shadow specimens, and numbers, strings and compositions with what their parts come to), and so does every imported repository component (see below); add your own pages and blocks for principles, guidelines and do / don't examples. Preview shows the finished site and Export HTML downloads it as a single file. Docs are saved with the project.


**Repository components in the documentation.** Once a repository's components are imported, the documentation has a **Repository components** section with a page for each one: its name, a live preview of every variant (or just the one, for a component without variants), a props table (types, defaults, the options of each variant and the descriptions from the code) and usage code with the import and the variants it can take. The preview is the real component running as it does in the repository, in a sandboxed frame; it is a block like any other, so the designer can add one to any page (**Add block**, then *Component preview*, *props* or *usage*), pick which component it shows, and switch it between one and all variants. The page for a component is named after where it is declared, so everyone who edits it edits the same page.

- **Preview** shows the site as it will be exported, with the live previews running, and **Export HTML** includes them: each preview is a page that carries its own runtime and is told what to show, so the exported file runs anywhere with network access to the package CDN, with no dependency on Motif being online. Without the repository connected the editor says what is missing, and the props and usage are still shown.
- Parts of a compound component (such as `TabsTrigger`) can't be shown without their parent, so their default page's preview shows the component's own error; change or remove that block, or document the parent.
## Reading a repository

Open **Source control** in a project and its **Repository** details to see how its repository is built (it is read when the project is opened; **Rescan** reads it again, or another branch). No token is needed for public repositories; private ones need a token with Contents read access. Motif parses the code without running it and reports:

- the stack: framework, language, build tool, styling system (Tailwind v3/v4, CSS modules, styled-components, Emotion, plain CSS), variants helper, entry files
- design tokens from CSS custom properties (with `.dark`, `[data-theme]` and `prefers-color-scheme` themes), Tailwind v4 `@theme` blocks, a Tailwind v3 config, and token JSON files
- React components with their props, defaults, doc comments, variants (from `cva` / `tailwind-variants` tables, `keyof typeof` lookups and string unions), hooks, and whether the package entry exports them
- how editable each component will be in the visual editor, and why

Nothing is written to the repository by a scan. Only React repositories are read so far.

**Where to start.** Opening a project reads its repository (its default branch) and brings the components in, with nothing to press. They appear in the Components panel under **Repository**. A repository with no React components says so, and a private one needs sign-in or an access token. The panel's **Repository** details have the scan with its report, and a choice of branch to scan.

## Previewing repository components

The repository's components are in the **Repository** group under Components. Opening one shows it on the canvas, running as the real component from the repository, with its own styles and tokens. With nothing open the centre lists the components, to open one from.

- **The canvas** pans and zooms. Scroll to pan; pinch, or hold Ctrl/Cmd and scroll, to zoom about the pointer; drag the background, or hold Space and drag anywhere, to pan. The buttons at the bottom left zoom, go to 100% and **Fit**, which keeps the component fitted as it loads until you move the view by hand. All of it works with the pointer over the component too: its page passes the wheel and Space up to the canvas, except that a part of the component that scrolls inside itself keeps its own scrolling, and that Space is left to a button or a field that has the focus. The **width** switch (Auto, 375 ... 1280) sets the width of the page the component runs in, so `md:` classes apply as they would in a browser of that width, whatever the zoom.
- **Props**: the right panel has a control for each prop (dropdowns from `cva` variants and string unions, switches for booleans, text) plus the content inside the component. **All variants** shows every combination side by side on the canvas, and the toolbar has Light/Dark and width switches.
- **Examples** show how the repository itself uses a component, taken from its demo, story and example files (`demo/`, `examples/`, `*.stories.tsx`, ...). Each usage becomes an example, and the parts of a compound component (`TabsTrigger`, `CardTitle`) are shown inside their parent. Values that only exist while the demo runs (state, props, local variables) are left out and handlers do nothing; the preview says what was left out. Overlays the demo opened with state are shown open.
- **Motif's tokens**: once tokens are linked to the repository, the tokens you have changed in Motif since the last sync are applied on top of the repository's own styles in every preview, so you see the components in your tokens before they are in a pull request. The palette button in the stage toolbar counts them and switches them off.
- **Update from repository** rescans and reports what is new, changed or gone.
- **How it runs**: the code is fetched in the browser, compiled with Sucrase and run in a sandboxed iframe with no access to Motif's storage or GitHub token, a Content Security Policy that blocks network requests and loads only React and the repository's packages from esm.sh and Tailwind's browser build from jsDelivr. Previews need network access to those CDNs, and image requests to https hosts are allowed.
- **Not supported yet** (the stage says so): CSS modules, Sass, `next/*` imports. Compound parts such as `TabsTrigger` render on their own only through their examples.
- Nothing is written to the repository.

## Editing repository components

Open a repository component and you are in **Design**, the mode you work in. The stage has four modes: **Design** (click an element to select it and change it), **Preview** (use the component: clicks reach it, and the right panel is its props), **Variants** (every variant side by side, and a canvas to work on like Design: the element you click is picked in every variant, and one edit, an added element, a resize, a new class, changes them all) and **Examples** (how the repository uses it).

**The frame.** The component sits in a labelled frame ("Banner · 640 × 110") that follows the light or dark theme. Above the canvas are the sizes designers think in (**Phone** 375, **Tablet** 768, **Laptop** 1024, **Desktop** 1280, **Auto**) and a width to type; the size that is on is marked. The frame's right edge can be dragged to any width, live. Scroll pans the canvas, Ctrl/Cmd and scroll zooms, and the chip at the bottom left zooms and fits.

**Working on the canvas.** The picked element shows its size, with its margin, padding and the gap between its children tinted (orange, green, pink), and handles to change them by dragging: the edges and corner resize it, a green dot on each side changes that side's padding (hold Alt to change the opposite side too), and the pink pill between its first two children changes the gap. The page shows the new size as you drag, and one edit is made when you let go. The size is turned into the repository's own terms: a token if one is that size, a step of the scale if one is near, and a value written out (`w-[184px]`) only where nothing is, so a drag lands on the design system by itself. A corner drag is one step to undo for a component with Tailwind classes. Keys, once you have clicked in the canvas: **Enter** picks the first element inside, **Esc** the one around it (and then lets go), the **arrows** go along its neighbours, **Alt+arrows** move the element itself, **Delete** removes it, **Ctrl/Cmd+D** duplicates it, **C**, **X** and **V** copy, cut and paste an element, and **Z** undoes. **Right-click** an element for a menu of the same things, plus wrapping it in a box, taking its wrapper off and copying its classes. Buttons say what they do, and what key does it, in a tooltip.

**First time here.** The first time a component is opened in Design, a short tour walks round the canvas, Add, the sizes, Layers and the panel, one card at a time, pointing at each. It never blocks anything: **Skip** or **Esc** ends it, and it isn't shown again once it has been left or finished. The question mark in the toolbar shows it again.

**Several sizes at once.** **Compare** in the bar over the canvas shows Phone, Tablet and Desktop side by side (each size is a switch, so Laptop can join or Tablet leave). Each is the real component at that width, so what a `md:` class does is there to see. Pick an element in any of them and it is picked in all; an edit made in one shows in all, and a size added later is brought up to date. Compare is for Design and Preview; Variants and Examples already show several things.

**Adding, moving and typing.** **Add** in the toolbar opens a palette: Box, Row, Column, Text, Heading, Image, Button, Link and List, then the repository's own components (added with their import, and with the props they need). Press one to add it inside the picked element (or after it, if that can't hold anything, or at the end of the component when nothing is picked); drag one onto the canvas and a line shows where it will go, between two elements or inside one, and it lands there when you let go. The same works for what is already there: drag an element by the grip beside its left edge, or drag a row in **Layers** (the top and bottom of a row put it before or after, the middle puts it inside). An element can't be dropped into itself, and each move is one step to undo, with the code re-indented to its new place. **Double-click** text to type in it on the canvas: **Enter** keeps it, **Esc** puts the old text back.

Click any element in the preview to select it, or pick it in the **Layers** panel on the left: a tree of what the component renders, read from its source, named for what things are (a Heading, a Box, a Button, a Link), with the HTML tag beside each, which opens down to the selected element and follows every change (components used inside it are shown but can't be picked; open them to edit them). The right panel has three tabs. **Design** has the element's name and what can be done to it (move, duplicate, delete), what the style is being edited for (see below), and the controls. **Props** has the component's props and variants. **Code** has the element's classes as text and its place in the markup (add an element, wrap it, change its tag, take its wrapper off). Every change is made to the component's real source and shown in the preview straight away.

- **State and where a style applies** are two controls: **State** (Default, Hover, Focus, Active, Disabled) and **Applies to** (Always, Dark, and the widths `sm` to `xl`). They are edited one at a time (a style that is both hover and dark isn't offered), so choosing one sets the other back to its plain value. Choosing a width sets the frame to that width so you can see it.

- **Layout, spacing, size, type, fill and border** are controls over the element's Tailwind classes: display, direction, gap, alignment, padding, margin, width, height, text size and weight, color, background, border, radius and shadow. Direction, justify, align and text alignment are rows of icons (pressing the one that is on takes it off), width and height have **Hug** and **Fill** beside the list of sizes, and the spacing controls are laid out as a small grid. A change replaces the class where it already is, so the diff is the one class that changed. Classes with a modifier (`hover:`, `md:`, `dark:`) are left as written. Direction, wrap, justify, align and gap only mean something in a flex or grid container, so choosing one on an element that isn't one makes it a flex container first (in the classes, or in its stylesheet's rule when the repository uses plain CSS), unless it already is one, is a grid, or is hidden; under a state (`md:`) the state gets the `flex`. It is one step of undo.
  - **Every control changes what the canvas shows.** The control writes the value where it will take effect: an element whose class has a rule in the component's stylesheet (`plain-box`) is edited **in that rule**, even in a repository that uses Tailwind, because a rule outranks any utility class (the panel says "Styles in Plain.css as .plain-box"); a property the element also sets in its own `style={{ ... }}` is **taken out of the style** when a value is chosen for it, because an inline style outranks classes (the panel lists what is set inline); and classes inside `cn()` conditions (`open && "p-4"`, `open ? "gap-2" : "gap-4"`) are read as classes of their own, with a value written into the plain classes and into every condition that sets the same group, so it shows whichever way the condition goes (the step says so). A tokens-named value in a stylesheet is written as the variable it is (`var(--radius-sm)` for the token `sm`). Not yet: components styled with CSS Modules (the preview says it can't show them).
- **Tokens**: the controls offer the repository's own design tokens, the ones it exposes to Tailwind (`--color-primary`, `--radius-md`, `--shadow-card`, `--text-*`, `--font-*`, named `--spacing-*` in `@theme`, or the same sections of a Tailwind 3 config), read by the last scan.
  - A **color** is a picker: the repository's color tokens with a swatch of each in the theme that is showing, a search box, the words `transparent`, `current`, `white` and `black`, and an opacity. Choosing a color keeps the opacity the class has (`hover:bg-primary/90` becomes `hover:bg-danger/90`); typing `name/50` sets both. A color typed or pasted as a value (`#4f46e5`, `oklch(...)`) finds the token that is that color; anything else that is typed is written as it is, so a Tailwind color such as `red-500` can still be used.
  - **Radius, shadow, text size, font and spacing** are lists with the repository's tokens first, each with what it is worth (`md · 8px`), then what Tailwind ships with and the repository has not replaced. Steps of the spacing scale say how big they are (`4 · 16px`), from the repository's own `--spacing` when it sets one.
  - A dot beside a label says the value is one of the repository's tokens. A value that is **written out** (`bg-[#4f46e5]`, `rounded-[8px]`, `p-[18px]`), or a Tailwind palette color in a repository that has color tokens, is marked as not a token, with a count for the element, and offered the token or step that is the same (**Use primary**, **Use md (8px)**, **Use 4.5 (18px)**) or, failing that, the closest, said to be only that. One press replaces it; an exact one leaves the component looking the same.
  - **Save as token…**: a written-out color, radius or spacing value with no token that is the same also has this button. Name it (the name is suggested and refused if taken) and **Save and use**: the token is added to the set linked to the repository (Repo sync), and the element uses it in the same edit, so `bg-[#1d4ed8]` becomes `bg-brand`. The preview shows it at once, and the token goes into the next sync the way a token made on the Tokens screen does: a color as a variable with its `@theme inline` alias, a radius or spacing value into the `@theme` block (so its name starts with `radius-` or `spacing-`, which the form adds), a stylesheet's token as a CSS variable. A token is usable the moment it exists, in every kind of repository: in the inspector, in the canvas and in the preview, with nothing sent first. What it is called in the repository follows its kind, so a class can name it (a radius made as `card` is `--radius-card` in `@theme`, or the `radius-card` key of a Tailwind 3 config, and its class is `rounded-card`; a spacing is `spacing-…`, a shadow `shadow-…`); the Tokens screen keeps the name it was typed with. Sent, it goes where the repository keeps tokens of its kind, and where it has none the block is made: a color in `@theme inline` (or right in `@theme` when that is where the repository keeps its colors), a radius, a spacing or a shadow in an `@theme` block added to the tokens stylesheet. Only a Tailwind 3 repository with no config of tokens, or one with no stylesheet to write to, says it can't. Undoing the element edit doesn't remove the token; undo that on the Tokens screen.
  - With the names known, `text-display` is read as a size when the repository has a `--text-display` and as a color otherwise, and `shadow-card` as a shadow where `shadow-primary` is the color of one.
  - Tokens the repository defines only as CSS variables, without a Tailwind name, are not offered, because no class names them. Colors are compared in the base theme. Token swatches follow the stage's theme and, when Motif's unsent token changes are shown in previews, those values.
- **Classes are found** in a plain `className`, in `cn(...)` / `clsx(...)` strings, and in `cva` / `tailwind-variants` tables: the base and the variant that is showing are edited, and a string written as `"a " + "b"` keeps its shape. Classes built at runtime or defined in another file are shown as such and not edited.
- **States and breakpoints**: the **State** selector in the inspector switches the controls between the plain classes and the ones for hover, focus, active, disabled, dark mode and the `sm`/`md`/`lg`/`xl` breakpoints. A state's value is written as its own class (`hover:bg-muted`, `md:gap-6`) next to the plain class it belongs to, in the same string, and the plain class is never touched; a property only the plain class sets is shown as inherited. Choosing dark turns the dark theme on and choosing a breakpoint sets the preview to that width; hover shows when the pointer is over the element. Focus and active can't be forced in a browser, so their classes are edited but not shown.
- **Text, order and structure**: edit an element's text, move it up or down among its siblings, duplicate it or delete it. The root of a component can't be deleted.
- **Insert, wrap and change**: the Structure section adds an element inside (first or last), before or after the selected one, from a small set of HTML snippets (div, text, heading, paragraph, button, link, list) or from the repository's own components, which are written with their usual starting props and the import they need, in the file's own style (reusing an existing import of the same module, refusing a name the file already uses). **Wrap in** puts the element inside a new div, row, column, section or component, **Unwrap** takes a wrapper with one element in it off, and **Tag** changes `div` to `section`, `h2` to `h3` and so on without losing classes or content. A new element is selected straight away. Elements can only be added beside another element inside a parent element, and never inside `img`, `input` and other elements that can't hold children.
- **Props and variants**: in Design the right panel's **Props** tab has a **Props and variants** section. For each `cva` variant group it lists the options: add one (it starts with the classes of the default option, so it looks the same until you change it, and then it is edited like any other option), rename one, remove one, and choose which is the default. **New variant group** adds a group to a `cva` call and wires it in: the cva call passes it and the component takes it from its props. For plain props it adds a prop (to the props interface or type and to the destructured parameters, with an optional default), changes or removes a default, and removes a prop that nothing in the component uses. The controls, All variants and defaults shown for the component follow these edits straight away. Renaming an option that is also used somewhere else in the file, removing the default or the only option, and removing a prop that is still used are refused with the reason, and so are shapes it can't place safely (props that aren't destructured, `cva` called without an object, variants that come from a type or a lookup table rather than `cva`).
- **Undo and redo** step through every change. Changes are sent with **Sync**, below. Nothing is written to the default branch directly.
- **Edits are kept** in this browser, for the repository and branch they were made on, so a reload (or closing the tab) doesn't lose them: the changes, their undo history (the last 60 steps) and the original text of each changed file. Updating from the repository keeps them too. If the default branch has changed a file you edited since, the stage says so and offers to give up the edits to those files: they aren't sent, because the pull request would overwrite the repository's change. Because the original text of the files is kept, for a private repository this includes its code, which stays in this browser like the access token does. Edits stay after they are synced, marked as in the pull request, until it is merged. Each undo step keeps only what it changed in a file (a few characters, not the whole file again), so a long session in a large stylesheet stays well inside what the browser allows; writes happen a moment after the last change and when the page is left, and the Sync panel says so if the browser refuses them.

## Syncing changes: one branch, one pull request

Changes made in the editor (edits to repository components, components made here, their stylesheets) are kept in the browser until you press **Sync**. Nothing is sent before that.

- **Source control** (the nav rail, or the button in the stage toolbar, which counts the files waiting) is the one panel for the repository, in the way of an editor's: **Pull** and **Push** side by side, then what is **waiting** (token changes and files), what is **in the pull request**, a note for the pull request's description, **Update branch** and **Discard changes** (all of them after a confirmation, or one file at a time). Each file can be opened to see its diff. The repository's details (the scan, the branch to scan, the report) are kept closed under **Repository**. The nav icon has a dot: amber for waiting, green for in sync, red for needing attention, and a blue one when the repository has changed since it was read.
- The first sync makes one working branch from the default branch (`motif/changes-…`), puts every changed file in **one commit** on it, and opens one pull request, "Changes from Motif". Every later sync adds one more commit to the same branch and brings the pull request's description up to date. There is never a second pull request while one is open.
- What is sent is a state, not a series of patches: the branch holds the default branch's files with the editor's changed files put in. So undoing an edit and syncing again puts the original text back, and giving up a file that was sent takes it out of the pull request again (a file made here is removed from the branch).
- The pull request is checked when the panel opens, when the window gets focus, and every minute while one is open. If the default branch has moved on, the panel says the branch is behind and **Update branch** brings it up to date through GitHub. If it conflicts, the panel says so and links to the pull request: resolving conflicts happens on GitHub.
- When the pull request is **merged**, the files that were sent become the starting point for further edits (only what you changed after the last sync is still a change), components made here are read from the repository like any other, and the next sync opens a new branch and pull request. When it is **closed without being merged**, your changes are kept and the next sync opens a new one.
- A file you edited that has changed on the default branch since is not sent (the stage and the panel say which); give up the edit to it, or the pull request would overwrite the repository's change.
- A failed request is shown with its reason and leaves the state as it was; sending again carries on from where it stopped.

Syncing needs you to be signed in with GitHub, or to have an access token with Contents and Pull requests read and write. The branch and the pull request are only known to the browser they were made in.

## The assistant

**Chat** (the sparkle in the rail, or Ctrl/Cmd+K) is an assistant for the design system. It needs `ANTHROPIC_API_KEY` set on the server; without it the chat says so. Where [accounts](#accounts) are set up, it is for people who are signed in, and limited per person. Each question is sent with what the assistant needs to answer about this project, and nothing else: the open component (its props and variants, and its elements with their classes and text), and the repository's tokens with what each is worth in the theme that is showing. It does not receive the repository's source files, the access token or where the code is kept. Anything in that context comes from the repository and is marked to the model as data, not instructions.

It can answer in words (review a component for accessibility or consistency, naming, advice) and it can **suggest**, as a card under its reply that you choose to apply or dismiss:

- **Changes to the open component**: a class group on an element (`text-size`, `bg`, `gap` ... in any state the inspector offers) or an element's text, named by the element's place in the component. They are checked before anything is shown: an element that isn't there, another component, a group or state the inspector doesn't have, a value with characters that could end a class, or one that isn't in a fixed list (`display: banana`) is left out, with the reason. Each change is shown as what it changes, from what the component has (`<h2> Text size lg → 2xl`), with values that are not tokens marked. **Apply** makes them with the same engine as the inspector, as **one step** to undo (Ctrl/Cmd+Z or the Undo button, in any mode), and they go out in the pull request like any other edit. If the component's elements have changed since the question, the suggestion is refused and you are asked to ask again.
- **New tokens**: colors (with an optional dark value), spacing, radius and shadows, added to Motif's token set, from where **Sync** puts them in your pull request. A name the set already has is left as it is. **Numbers** (with a unit and what they are used as), **strings** and **compositions** can be suggested too (a composition's parts name the tokens they are: `font-size` is `text-xl`); the card says which stay in Motif for now, since the repository's sync doesn't carry them yet.

It cannot add, remove or move elements, change props or variants, or edit anything the inspector can't. The chat starts again when another project is opened.

## The Tokens screen

Tokens are what a design system is made of, so the screen reads like one.

- **Palette**: a color group is a **ramp** (`gray-50` … `gray-900`): swatches in step order, each with its hex, **Light and Dark side by side** (or one theme, from the theme bar above). Press a swatch to edit it: the value for each theme (hex, `rgb()`, `oklch()`, any color Motif can read; what isn't one is refused), the picker, how it reads on white and on black (WCAG grades), its group, copy as hex or `var()`, duplicate, delete. **List** shows one row per token instead, with the values editable where they stand. The view you used last is remembered. Spacing is shown as bars with px and rem, radii as shapes, shadows as cards, text styles as specimens.
- **Collections**: the sets of the Tokens screen are collections (a *Primitives* set of raw colors, a *Semantic* one whose colors are colors of it; see Aliases). Each has a name and a note of what it is for, shown under the name (the pencil edits both; Enter or leaving the fields takes them), and they can be put in the order you want (the arrows). **Delete** asks first: it says what goes (`12 colors, 3 numbers`) and how many aliases of colors in other sets lead into it (those colors keep the colors they have now and stop following), and the set that is synced with the repository can't be deleted while it is. Every one of these is a step of undo, and the order and the notes are saved with the project.
- **Themes**: the themes of a set are in a bar over its colors (themes only change colors; radius, spacing and shadows are the same in every theme). **All** shows every theme side by side, a theme's name shows it alone (and makes it the theme that is open, the one a new theme starts as a copy of). **Add** opens a small form: the theme's **name** (one a theme already has is refused), the theme it **starts from** (a copy of it; the open theme to begin with), and **Make a dark version**, which turns each color's lightness around while keeping its hue (white becomes a soft dark, dark text becomes light text; a color that is another token stays that token, and a name with *dark* or *night* in it suggests it); each theme has a **⋯** menu (also on a right click, and a double click renames) with **Rename**, **Duplicate** (a copy next to it, with its values and the colors that are other tokens) and **Delete** (a set keeps at least one theme; it asks first, says how many colors lose their value in it, and, for a theme the repository has, that the next Pull brings it back). In the set that is synced with the repository each theme is marked with its name there (`light`, `dark`), or *Motif only* when the repository doesn't have it yet. Each of these is a step of undo; switching themes isn't, and undo leaves the open theme where it was. With more than one theme the chips **Differ between themes** and **Same in every theme** narrow the colors to the ones that are not the same in every theme (or are), and picked colors can be given **the colors of another theme** (**Copy between themes**; an alias goes along as an alias), as one step of undo. Deleting a theme that is the repository's only deletes it in Motif: the repository keeps it, and the next **Pull** brings it back as a theme of the set with the repository's values (a sync never deletes anything from the repository).
- **Adding**: **Add** on a group opens a row for a new token with its name already suggested (`primary-950` after `primary-900`). Type a hex and press Enter: it is added and the row stays for the next, so a ramp is a run of hex codes. A color pasted where the name goes is taken as the value. **New group** makes a group. **New token** (in the bar) asks what the token is first: a **Color**, a **Number** (a value with its unit, `px`, `rem`, `em`, `%` or none, and what it is *used as*: font size, line height, font weight, letter spacing) or a **String** (text, used as a font family or not said), and below them the kinds that have their own tab (spacing, radius, shadow, text style). Numbers and Strings have their own tabs, are arranged, copied, moved, undone and exported (JSON, CSS) like any token, and are saved as typed tokens; they are Motif's own until the repository's sync reads and writes them. Spacing and radius in pixels, which sync, keep their tabs.
- **Adding many**: **Add many…** opens a dialog with two tabs, and either shows what adding would do before anything changes (a token is *New*, *Changes it* if one of that name is there with another value, or *Already there*; each has a box, and what couldn't be read is listed with why). **Paste** takes CSS custom properties (read the way a repository's are: a `.dark` block fills the Dark theme and `:root` the Light, `@theme` blocks work, and a `var(--x)` value is an alias when it is a color of the text or of the set, and listed as left out with why when it isn't), a **design tokens (W3C) file**, or **lines**: `primary #6366f1`, `space-4: 16px`, `--accent: rgb(1 2 3);`, or just a list of colors (`#111827, #374151 #6b7280`), which get numbered names. Each value is given the type it has: a color, a shadow, a length in pixels (a spacing, or a radius when the name says so), a **Number** when the name says it is a font size, a line height, a font weight, letter spacing or a ratio (it keeps the unit it was written in: `1.125rem` stays rem, `700` has none) or when it is in `em` or `%`, and otherwise a **String** (a font family when the name says so). A design tokens file's `fontFamily`, `fontWeight`, `number` and `dimension` tokens are read the same way, and a color or dimension written as an object (`{ colorSpace, components, hex }`, `{ value, unit }`) is read from it. **Scale** makes tokens from one value: a **color ramp** from one color (50 … 950 in OKLCH, your color kept exactly at the step it is nearest to, the other steps in its hue and clipped to what a screen can show, and an option to turn the ramp over for the Dark theme), or a **spacing** scale from a unit, a **radius** scale from the medium radius, or a **type** scale from a size and a ratio, or a scale of **numbers** (a base, a unit, a ratio, a name and what it is used as: `scale-1` smallest, growing by the ratio). Adding is one step of undo.
- **Organizing**: **search** (press `/`) finds tokens by name, group or value; the chips narrow to *Changed* since the last sync, *Not in repository* or *Read-only*. Click a name to rename it in place, and double-click a group's name to rename the group. Pick tokens with the checkboxes (or Shift-click a range, Ctrl/Cmd-click to add), and a bar offers **Move to group**, **Move to set**, **Duplicate** and **Delete** (which asks once more, and says so when the repository will bring a token back at the next sync). **Drag** a token by its handle onto a group's header to move it there, or between two tokens to put it there. **Regroup by name** files every color under the group its name says: a ramp is a group, `primary` and `primary-foreground` are one. Keys: `Delete`, `Ctrl/Cmd+D`, `Ctrl/Cmd+A`, `Esc`.
- **Aliases (semantic tokens)**: a color can be another color, in each theme on its own: `background` is `gray-50` in Light and `gray-900` in Dark. In a color's editor, **Make it another token…** under a theme picks one (a token that would lead back to this one isn't offered); the color then shows as that token's and **follows it** when it changes, through any number of steps. **Detach** keeps the color it is and stops following; typing a color over an alias does the same for that theme. To do it to several colors at once, pick them and press **Make alias…** in the bar above the list: choose, for each theme, the token they all become, or *Detach* to keep their colors (one step of undo; one that would lead back to itself is refused and counted). The palette marks these colors with an arrow, the list names the token, and search finds them by it. The editor of a token says what uses it, and deleting it leaves those with the color they had. In the repository an alias is `--background: var(--gray-50);`: Sync reads it that way, compares it as such and writes it back the same (the CSS and design tokens exports write references too). Pasting `--background: var(--gray-50)` into **Add many…** makes one. **Across sets**: a color can be a color of *another* set, which is how a set of semantic colors points at a set of primitive ones (`Semantic / surface` is `Primitives / gray-50`). The picker lists the colors of the set first, then those of each other set under its name, the chip says `Primitives / gray-50`, **Used by** lists the colors of every set that are this one (with their set), and **Make alias…** offers the colors of every set. A color follows the theme of the other set that has the same name (Light is Light), and else the theme that set has open. Moving a color to another set, or the color it is, keeps what is an alias an alias (the alias then names its set); deleting a set leaves every color that was one of its colors with the color it came to. Aliases are for colors; `@theme inline { --color-primary: var(--primary) }` (the Tailwind mapping layer) stays a mapping and is not shown as a token.
- **Compositions**: tokens that go together as one. **New token → Composition** asks for a name and what it is made of: **Typography** (a font family String, a size, a weight, a line height and letter spacing), **Shadow** (x, y, blur, spread, a color, and *Inset*) or **Custom** (parts of your own: add a Color, Number or String part, rename it, remove it). Each part is a value of its own or **another token of its type** (a Number part can be a Number, a spacing or a radius; a part can be a token of any set, listed under its set), and then follows it: change `text-xl` and every composition that has it changes. A token that is deleted (or its set) leaves the part with the value it had; undo brings the token and the link back. The row shows a sample (the text style, the shadow) and what the parts come to, search finds a composition by them, and compositions are arranged, moved between sets, duplicated and undone like any token. They are Motif's own for now: the repository's sync doesn't carry them yet (they are in the JSON and CSS exports, as `typography` and `shadow` tokens, or as a group of tokens for a custom one). The fixed **Typography** and **Shadows** tabs stay for the text styles and shadows the repository reads and writes.
- **Where tokens are used**: a scan of the repository also counts where its code uses each token: class names (`bg-primary`, `hover:bg-primary/90`, `-mt-gutter`, `rounded-card`, `@apply`) and `var(--token)` in components and stylesheets (a token given to Tailwind by `--color-primary: var(--primary)` isn't counted as a use of itself). A token of the repository's shows **used 11×** (hover for which components), **unused** when nothing was found, and its editor says where; the **Unused** chip lists those. Deleting a token that is used says so (deleting in Motif doesn't change the code, and the repository brings the token back at the next sync). It reads what a scan can see: a token used only through a computed class name, a Tailwind config's `theme()`, or by other code reads as unused, so check before removing one from the repository. A project scanned before this was counted shows a disabled **Unused** chip until the repository is scanned again.
- **Renaming a repository's token**: **Rename in repository…** (in a token's editor, or the pencil on a spacing, radius or shadow row) changes the name **everywhere the repository uses it**, as one change to your pull request. Type the new name (a name that is taken, isn't a name, or is a Tailwind token that loses the prefix that gives it a class, such as `color-` or `radius-`, is refused with the reason) and **Find places**: Motif reads the repository's code (every `.css`, `.ts`, `.tsx`, `.js`, `.jsx`, `.mdx` and `.html` file, demos, stories and tests included, as the pull request will have it; a repository with more than 800 is refused rather than half renamed) and lists the files and how many places each has. **Rename and add to pull request** then changes the declaration in every theme, the `@theme inline` mapping that gives Tailwind its class, every `var(--name)`, every class that names it (`hover:bg-primary/90` becomes `hover:bg-brand/90`; `primary-foreground` is another token and is left alone) and `@apply` and comments in stylesheets, and renames Motif's own token and the colors that are it. Nothing is sent until you press Sync, which sends it with everything else; the files are in the Changes list and can be given up there, and undo on the Tokens screen puts the name back. It can't see class names built while the page runs (`bg-${x}`), and Markdown files are left as they are. Tokens defined in a token JSON file, or computed in a Tailwind config, can't be renamed yet.
- **Undo**: **Undo** and **Redo** (Ctrl/Cmd+Z, with Shift to redo) take back what was done on the screen, a bulk move or a pasted batch being one step. A sync or the assistant changing the tokens ends the history, so undo never takes back something it didn't make.
- **What belongs to Motif and what to the repository**: groups, their order and the sets are Motif's own and are never sent. A token the repository names is renamed with **Rename in repository…** (below), not in place, because Sync matches it by that name (it shows a lock where it is defined somewhere Motif can't edit yet, and can't be renamed there); a copy of it, a token added here, or one moved to another set is Motif's own until it is synced.

## Syncing tokens with a repository

**Pull** (in the Source control panel, and the refresh button of the Components panel) reads the repository again and takes it in: components that changed, and token changes from the repository, merged with what was changed here; only a value that was changed in **both** places asks (a dialog with the two values side by side: keep Motif's, which goes out with the next push, or take the repository's; *Decide later* leaves the tokens for the next pull). A dot on the refresh button, and a note on Pull, say when the repository's default branch has moved since it was read (looked at every minute and when the page is looked at again). Nothing that was changed here and not sent is touched.

Open **Source control** with a repository connected to see the link: the set that is linked to the repository, which is made when the repository is first read. Sending tokens is **Push** (see above), and **Pull** resolves what the repository changed. Pushing needs a token with Contents and Pull requests read and write.

- **The repository has tokens in its stylesheets** (Tailwind 4 or plain CSS): they are **converted when the project is first opened**, with no question and nothing written to the repository: one Motif set, one theme per repository theme (`:root`, `.dark`, `[data-theme="dark"]`…), colors (`oklch`, `hsl`, `rgb`, hex; a color that is another variable stays a reference), px and rem lengths and `@theme` shadows, each keeping the name its variable has (`--primary` stays `--primary`). What can't be kept as a token stays in the stylesheet and is listed with why: `@theme inline` aliases, `calc()` and `color-mix()`, fonts, variables inside `@media` or `@layer`. The first **Push** (or **Add to pull request** in Source control) carries the conversion as one step in your pull request: the design tokens files, `tokens.config.json`, the Style Dictionary config and script, the generated stylesheet, the converted declarations taken out of your stylesheets, and the generated stylesheet imported after the Tailwind import. The step's lines say **`Check: 41 variables, all identical`** (every variable in every theme compared as it resolves: colors as colors, lengths in px, aliases followed) or list the ones that would come to a different value. If the stylesheets change in the repository before you push, Pull first. Projects that were linked to a repository's stylesheets before this keep their link and the in-place stylesheet edit described below; so do Tailwind 3 repositories (converting them comes later).
- **Later syncs**: **Pull** compares Motif and the repository against the last sync. Changes from the repository are applied to Motif; changes made in Motif go into your pull request when you press **Push**, as an edit of the stylesheet in place, in the notation it already uses, so the diff is only the values you changed (a value changed back is written exactly as the repository had it). The panel counts them as token changes. A value changed in both places asks which to keep when you pull; everything else is still sent. New tokens are added following the repository's own conventions (variables per theme, the Tailwind alias, `@theme`).
- **A project linked to the stylesheets (older projects, and Tailwind 3)**: that link sends only the colors, spacing, radii and shadows of one set, written into the stylesheet and config; Numbers, Strings, compositions and the tokens of other sets stay in Motif, and the panel says so. For Tailwind 4 and plain CSS, **Move to design tokens files** (in Source control, under the token link) moves the project to the files, which carry every token: the tokens become what the stylesheets come to (the way a new project takes them in, keeping the groups you made), and what was waiting is kept: a color changed here is changed there, a token made here is still made, one deleted is still deleted, and the Numbers, Strings, compositions and other sets are as they were. The first push then writes the files, as for any repository whose tokens are variables in its stylesheets. It is refused while token changes are in the pull request (merge or discard it first) and for Tailwind 3.
- **Design tokens files**: a repository whose tokens are [design tokens (DTCG)](https://www.designtokens.org/) JSON (a `tokens.config.json` and the files beside it, which Motif's format and Style Dictionary build the stylesheet from; see `src/lib/dtcg/README.md`) is read as one thing for **every** set: its sets, themes, colors that are other colors (in any set), numbers, strings and compositions come in the first time (into a project that has no tokens yet; one with tokens of its own says so and is left alone). **Pull** merges the repository's files with Motif's tokens token by token and theme by theme, takes what changed on one side, and asks about a value changed on both (a color is one value). Nothing is deleted from the repository by a sync: a token deleted here comes back. **Push** puts Motif's token changes into the pull request as changes to those files (only the values that changed, in the text the files already have) and writes the stylesheet they come to when it is one Motif's build writes. A repository with no tokens starts this way (see Starting from an empty repository). A setting for one file or a file for each set, and converting a repository whose tokens are in its stylesheets, come next.
- **Conflicts**: when both sides changed the same value you choose which to keep.
- **The repository has no tokens**: **Add to pull request** puts every set in as design tokens files with the stylesheet they come to (wired into Tailwind v4 and imported from its stylesheet when there is one) and what builds it. That is the one explicit step; later token edits follow on their own at Sync.
- **One pull request.** Token files, the Tailwind add-on and components are planned against the repository *as your pull request will have it* (the default branch with your changes in it), so each step builds on the one before: a second new component adds to the first one's barrel, Tailwind rewrites a tokens file that is still only in the pull request, and so on. When the pull request is merged, the link moves on only for the tokens it changed, so a token the repository changed on its own still shows as coming from it. Tokens go to the default branch's pull request: a link to another branch says so and isn't sent.
- **Syncing never deletes a token from a repository.** A token deleted in Motif comes back on the next sync, and one removed in the repository is removed from Motif.
- **Tailwind 3 repositories.** Tokens are read from `tailwind.config.js` (`theme` and `theme.extend`: colors, `borderRadius`, `boxShadow`, `spacing`, `fontFamily`, `fontSize`) and from the CSS variables it points at. A color kept the way shadcn/ui does (`--primary: 222.2 47.4% 11.2%;` with `primary: "hsl(var(--primary))"` in the config) is one token that is the variable: it is read as the color the channels make, and an edit is written back **as channels** (`0 100% 50%`, with the digits it needs to read back exactly), in the same variable, in each theme. A value written out in the config (`md: "0.5rem"`, `card: "0 1px 2px …"`) is changed **in place** in the config file, keeping its quotes, comments and layout; a value that is computed there (a const, a joined string) is left alone and listed as read-only with that reason. A new token is a `theme.extend` entry named for its class (`radius-card` is `card` in `borderRadius`), and a new color is a variable of channels in each theme plus an entry that wraps it; a config has no themes, so a new radius, spacing or shadow has only its base value. **Rename in repository…** works too: the config key moves with the token (a `DEFAULT` that shares its group is taken out of it, so `primary-foreground` keeps its class name), together with the variable, the classes and the rest. **The preview works too** (the stage and the canvas): Tailwind 3 has no browser build, so Motif serves its own, `public/motif-tailwind3.js`, made from the project's `tailwindcss` 3 (with `tailwindcss-animate` and the official `forms`, `typography`, `aspect-ratio` and `container-queries` plugins) by `scripts/build-tailwind3.mjs` (`npm run dev` and `npm run build` run it first; it isn't committed). The page runs the repository's own `tailwind.config.js` as one more module of the sandbox, and builds its stylesheet (the `@tailwind` directives, `@layer` and `@apply` of the repository's CSS) in the browser, the way the repository's own build would: the same CSS, byte for byte, as `tailwindcss` makes in Node for the same input. The classes it reads are the ones in the code of the modules and the page as it is, so a class you just set is built a moment after, and the repository's `.dark` styles apply with the preview's dark theme. Motif's own token changes show too: a color the config wraps as `hsl(var(--primary))` as the channels of that variable, a value the config holds (a radius, say) and a token only Motif has as entries added to `theme.extend`. **Documentation pages and the exported site work as well**: a page that has to run without Motif can't carry the engine (it is large and is Motif's to serve), so Motif builds the page's stylesheet first, by running the page out of sight and taking the stylesheet it built, and the page carries that. The exported file then has no engine and no address of Motif's in it. **New component** makes a component of Tailwind classes in a Tailwind 3 repository, as it does in a Tailwind 4 one. Not for Tailwind 3: a config that needs Node (`require("path")`, files it reads) or a plugin that isn't one of those above, and adding or changing the Tailwind version (Motif adds v4 only to a repository with no Tailwind, and doesn't change versions).
- Tokens defined in a token JSON file are read, but writing changes back to them is not supported yet.

## Look and feel

Motif is built with its own design system (the brand: a cream surface, ink text, one blaze orange for the main action, cobalt for what is selected). Everything in it is a CSS variable in `src/app/globals.css` and a name in `tailwind.config.ts`, so changing the look is changing those two files.

- **Colors**: `surface`, `surface-raised`, `surface-sunken`, `ink`, `ink-muted`, `line` and `line-soft`; the accents `blaze` (primary actions, with `on-blaze` text, never white), `cobalt` (selection, links), `sun`, `mint` and `bubblegum` with a `-soft` tint each; `success` and `danger` for status. Each has a light and a dark value. The older names (`bg-surface-base`, `text-text-primary`, `border-surface-border`) point at them.
- **Theme**: the app follows the system's light or dark setting until a choice is made (the three buttons on the project list, and in the editor).
- **Type**: Bricolage Grotesque for display, Figtree for the interface and DM Mono for code, served with the app (no request to a font service). The scale is 12, 14, 16 and 18px; body text is 16px.
- **Controls**: buttons, inputs and selects that have a text label are at least 44px tall; icon-only buttons stay small. The top bars are 56px.
- **Shape**: radii of 6, 10 and 16px, flat surfaces with a one-pixel line, a shadow only for menus, tooltips and dialogs, and a 3px focus ring on everything that takes focus.
- **Mark**: `src/components/Logo.tsx` (the mark, the lowercase wordmark and the pattern band of its four shapes), `public/brand/` and the favicon `src/app/icon.svg`.

## Building on a server with an old glibc

`npm run build` uses Webpack (`next build --webpack`). Next 16 builds with Turbopack by default, which needs Next's native compiler, and that needs glibc 2.29 or newer; on an older host (some shared hosting) Next falls back to its WebAssembly compiler, which only Webpack supports. Webpack builds the same app everywhere, so the build doesn't depend on the host. `npm run dev` still uses Turbopack.
